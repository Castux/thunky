# Implementation — 4. Core IR and Lowering

Lowering (`internal/core/lower.go`) turns the resolved AST into the **Core IR**
(`internal/core/core.go`). Core is the representation on which laziness, scoping,
and desugaring are all made explicit, so the bytecode compiler that follows
([5.Bytecode and Compiler](5.Bytecode%20and%20Compiler.md)) is a mechanical,
syntax-directed pass. Three things happen here:

1. **Names become addressing modes.** Every `Var` carries an `Addr` that is
   one of: a local frame slot, an upvalue (captured) slot, or a module slot.
2. **Laziness becomes explicit.** Every position that must stay unevaluated until
   demanded — a function argument, a data field, a let/module binding — becomes a
   `Thunk`. Everything else is built directly. This is the defining feature of
   the spineless tagless G-machine: the graph of deferred computations is named in
   the IR rather than discovered at run time.
3. **Sugar is removed.** Operators (`>` `<` `*>` `<*`), list and string literals,
   and list patterns are desugared into applications, cons chains, and nested
   arity-2 tuple patterns. The compiler never sees them.

## The Core types

```go
type Expr interface{ coreExpr() }

type Num     struct{ Val float64 }                 // unboxed numeric literal
type Const   struct{ Val Value }                   // prebuilt value: string list, empty tuple, builtin
type Stdin   struct{ Bytes bool }                  // stdin, or bstdin when Bytes
type Var     struct{ Addr Addr }                   // resolved reference
type App     struct{ Head Expr; Args []Expr; Pos SourcePos }
type Compose struct{ Forward bool; Fns []Expr } // *> (forward) or <*
type Cons    struct{ Head, Tail Expr }
type Tuple   struct{ Fields []Expr }           // arity 0,1,3,4,… (2 is a cons)
type Let     struct{ Binds []Bind; Body Expr }
type Lambda  struct{ Cases []Case; Free []Addr; Frame int; NoMatch SourcePos } // + FreeNames, debug
type Thunk   struct{ Body Expr; Frame int; Name string }                      // + Pos, debug
                                               // no Free: a thunk captures the whole
                                               // enclosing frame, not a minimal list

type Addr     struct{ Kind AddrKind; Slot int; Module string } // Local | Upvalue | Module
type Bind struct{ Slot int; Name string; Body Expr }   // Body is a Thunk
type Case struct{ Pattern Pattern; Body Expr; Frame int }
```

Patterns are normalised to three shapes — `PatternVar{Slot, Name}`,
`PatternConst{Val}` (always a number after desugaring), and
`PatternTuple{Fields}` (arity 2 is a cons). A list pattern becomes a nested
arity-2 tuple chain ending in the empty-tuple pattern, and a string-literal
pattern becomes a nested cons of code-point constant patterns, so the compiler
only ever emits one matcher shape.

A `PatternVar` keeps its source `Name` and a `Thunk`/`Bind` keeps its
binding `Name` because those names are observable: they appear in reduction traces
and in how `show` labels a thunk (see [6.The G-machine](6.The%20G-machine.md)).

## Demanded vs lazy positions

Lowering an expression depends on whether its value is demanded now or must stay
lazy, mirroring the two compiler procedures that follow it. There are three
mutually-recursive lowering functions:

- **`lowerTail(e)`** — demanded position. An application flattens its spine into a
  `App`; a pipe folds into nested single-argument `App`s; a let becomes a
  `Let` whose body is itself in tail position; a composition is a value;
  everything else is a value.
- **`lowerArg(e)`** — a lazy position (an argument or a data field). Anything that
  could force when entered — an application, a pipe, a let — becomes a
  `Thunk`; atoms and pure constructors are built directly, since building them
  forces nothing.
- **`lowerValue(e)`** — builds a value: a literal, a constructor (cons / tuple /
  list), a name, a closure, or a composition. Its compound parts are lowered with
  `lowerArg`, so the fields of a constructor stay lazy.

This split is what guarantees the compiler's invariant that a `App` only ever
appears in tail position (as a body, a let-binding body, or the head/nested-head
of another application) — never as a constructor field or an argument, where it
would have to leave a single value. Such positions always hold a thunk or an atom.

### Why operators desugar the way they do

A pipe `a > b > c` is `c (b a)` and `a < b < c` is `a (b c)`;
`lowerPipe` builds the nested applications and carries the folded remainder in a
lazy thunk. A composition `f *> g` reduces, when applied to `x`, to `g (f x)`;
`lowerCompose` records the operands in source order and a `Forward` flag, and the
compiler emits the `MakeCompose` instructions that build the runtime
`Composition` value. Arithmetic is *not* an operator in Thunky — `add`, `mul`,
… are ordinary builtin names applied as functions, so they lower to a `core.App` of a
builtin `core.Const` and saturate through the normal application spine.

## Slots, frames, and capture

An *activation* is the program body, a module binding, or a lambda case — anything
that runs over its own local frame. `FrameBuilder` tracks slot allocation for one
activation and the upvalues a nested lambda captures from it.

- **Pattern variables and let bindings** allocate a local slot in the current
  frame. Let slots for a whole group are allocated before any binding body is
  lowered, so mutual recursion resolves. A lambda's cases share the frame: each
  case resets the slot counter and the lambda's `Frame` is the largest case's size.
- **Thunks capture the whole enclosing frame** by reference and address it with
  the enclosing slot numbers. There is no per-thunk capture list and no slot
  renumbering, and `letrec` falls out for free — a binding thunk references the
  shared frame, which is fully populated before any binding is forced. A thunk's
  body is therefore lowered in the *same* `FrameBuilder` as its surroundings, so
  a `let` inside an argument thunk allocates into the enclosing activation's frame.
- **Closures capture a minimal free-variable list.** Closures escape, so retention
  matters; `resolveUpvalue` threads each captured variable down through every
  intervening frame, producing the `Free []Addr` list that the compiler turns into
  a capture array. A reference to an outer variable becomes an `AddrUpvalue` slot;
  a reference to this frame's own slot stays `AddrLocal`.

## Reachable module bindings

A program typically imports far more than it uses: `import list` makes every
public binding of `list` visible, but a given program may call only a handful.
Lowering compiles only the bindings the program actually reaches, treating the
rest as dead code.

`reachableModuleBindings` computes the live set as a transitive closure over the
*references* relation: a module binding is live if the program body references it,
or a live binding's right-hand side references it. It needs no new analysis — it
reads the resolver's facts, treating a plain name that resolved to a module binding
(`ResolveModule`) or any qualified name as a reference, and runs a worklist until
no new binding is added.

Dropping a dead binding is observationally transparent. Laziness already means an
unreferenced binding never runs — its thunk would be built at startup and never
forced — and the resolver checks every module independently of reachability, so
pruning removes no diagnostic. The payoff is that the dead binding costs neither a
compiled span nor a startup thunk and frame.

Slots are then assigned **densely over the survivors**, per module in declaration
order: the *k*-th surviving binding of a module gets slot *k*. Because the compiler
emits the module's bindings in that same order and the machine builds the module
environment positionally, a binding's slot is exactly its index in that
environment, with no gaps left by the pruned bindings — so nothing downstream of
lowering needs to know that pruning happened.

## Memoisation (call-by-need everywhere)

**Every thunk memoises.** Forcing a thunk runs its body once, writes the
weak-head-normal-form result back, and shares it from then on — there is no
call-by-name thunk, and no `Update` flag to choose between strategies. Whether a
thunk is a let binding, a module binding, a pattern binding, or an anonymous
argument / field / pipe thunk, it is computed at most once.

This matters for the output builtins. `peek`/`show`/`write`/`bwrite` return their
argument, so the same thunk can be reached again after it has already been
forced; because forcing memoised, the side effect (the print) happens exactly
once rather than repeating. It is also a measurable win on ordinary code: a
multi-case lambda forces its argument to test a number/tuple pattern and then
binds the *same* thunk in a fallthrough case, so under the old call-by-name
scheme the argument was recomputed between the match and the bind. (Earlier
versions distinguished call-by-need from call-by-name with an `Update` flag; it
was a remnant of the tree-walker the golden files were first captured from, and
re-running effects was a bug, not a feature.)
