# Implementation — 0. Overview

This document series describes how the *Thunky* implementation works
internally: how source text becomes a running program, how lazy evaluation is
realized, and how the runtime represents and reduces values. It is a companion
to [LANGUAGE.md](../LANGUAGE.md), which defines the language itself; here we are
concerned with *mechanism* rather than *meaning*.

The execution engine is a single **spineless tagless G-machine**. Source is
lexed and parsed into a pure AST; the AST is resolved and lowered into a **Core
IR** that makes laziness explicit (every deferred computation is a thunk, every
function a closure with an explicit capture list); the Core is compiled to a flat
bytecode; and the G-machine reduces the program body to weak head normal form,
printing whatever the program's side-effecting builtins emit along the way.

Correctness is pinned by golden tests: `tests/cases` holds a `*.expected` file
for every case, holding its combined stdout and stderr byte for byte, plus a
`*.exit` file for the cases that are meant to fail. `tests/run.sh` (and
`tests/run.ps1`, on Windows) checks the engine against them; both run in CI.

## Project structure

The implementation is split into six packages under `internal/`, enforcing
boundaries between the stages:

- **`source`**: The foundation. Holds `SourcePos`, `Log`, and `RuntimeError`.
- **`syntax`**: The frontend. Holds the lexer, parser, AST, and resolver.
- **`value`**: The runtime representation. Holds the `Value` type and its
  associated services (forcing, display, primitives, builtins, stdin).
- **`core`**: The intermediate representation. Holds the Core IR and the
  lowerer that produces it from the AST.
- **`backend`**: The execution engine. Holds the bytecode compiler and the
  G-machine itself.
- **`types`**: The type analysis. Infers a structural type for every expression
  from the resolved AST, and checks it against the signatures `-->` comments
  declare; an inspection mode, not a stage of execution (see
  [7.Type Analysis](7.Type%20Analysis.md)).

The root `main.go` orchestrates these packages.

## Pipeline overview

Running a program proceeds through six stages:

```text
source ─Lex─► tokens ─Parse─► AST ─Resolve+Lower─► Core ─Compile─► Bytecode ─Run─► value
                              (pure)   (names, slots,    (flat      (G-machine)
                                        capture, desugar,  []Instr)
                                        explicit thunks)
```

1. **Lex** (`internal/syntax`) turns the source bytes into a flat slice of
   tokens, discarding whitespace and comments (see [1.Lexer](1.Lexer.md)).
2. **Parse** (`internal/syntax`) builds an abstract syntax tree from the
   tokens by recursive descent. The AST is *pure* — no later pass writes back to
   it (see [2.Parser](2.Parser.md)).
3. **Resolve** (`internal/syntax`) walks the tree to resolve every
   name, rejecting undefined and duplicate names and unimported modules. It
   produces *resolution facts* without mutating the AST (see [3.Resolver](3.Resolver.md)).
4. **Lower** (`internal/core`) turns the resolved AST into the Core IR: names become
   addressing modes (local slot, upvalue slot, module slot), frame slots are
   assigned, closures get a minimal capture list, operators / lists / strings /
   list-patterns are desugared, and every lazy position becomes an explicit
   thunk (see [4.Core IR and Lowering](4.Core%20IR%20and%20Lowering.md)).
5. **Compile** (`internal/backend`) translates the Core into one flat `[]Instr`
   array; every body (program, module binding, lambda case, thunk) is a
   PC-addressed span (see [5.Bytecode and Compiler](5.Bytecode%20and%20Compiler.md)).
6. **Run** (`internal/backend`) reduces the program body on the G-machine: an
   explicit reduction stack of argument and update frames, push/enter
   application, and thunk forcing by running compiled bodies (see
   [6.The G-machine](6.The%20G-machine.md)).

Modules referenced by `import` clauses are loaded, parsed, and resolved before
execution begins; lowering then compiles only the bindings the program actually
reaches.

## Inspecting the stages

The intermediate representations can be dumped as text rather than run:

| Flag              | Emits                        | Extension     |
| ----------------- | ---------------------------- | ------------- |
| `--dump-ast`      | the parsed AST               | `.ast`        |
| `--dump-core`     | the lowered Core IR          | `.ir`         |
| `--dump-bytecode` | the compiled bytecode        | `.bc`         |
| `--types`         | types per binding, and checks | `.types`      |
| `--types-all`     | inferred type per expression | `.types-all`  |

Any of them switches the compiler into inspection mode: the requested stages are
emitted to stdout and the program is not run. Several can be combined. Adding
`--to-file` writes each stage to a file beside the program instead, named after
it with the extension above — useful for diffing two versions of a stage.

Each dump is an indented, human-readable rendering:

- The **AST** dump (`internal/syntax`) shows structure and literal values exactly as
  parsed, with no resolution or slot information.
- The **Core** dump (`internal/core`) shows what lowering decided: every name as an
  addressing mode, every lazy position as a thunk, and the desugaring of sugar.
- The **bytecode** dump (`internal/backend`) disassembles the flat `[]Instr` array
  in PC order, printing a header at every span entry.
- The **types** dump (`internal/types`) infers a structural type for every
  expression and prints one line per binding, followed by the places that did not
  check out — the language is dynamic, but the shapes are recoverable from the
  builtins, the literals and the patterns, and a declared one is verified against
  the code and its call sites (see [7.Type Analysis](7.Type%20Analysis.md)).

## Runtime services

The runtime representation — the `Value` tagged union and the heap types — lives
in `internal/value` and is shared by everything downstream of the machine:
`show`/`peek` rendering, structural equality and full-normal-form forcing, the
lazy stdin streams, the numeric/comparison prim kernels, and the structural
builtins. Because a weak-head-normal-form result is an ordinary `Value`, all of
these are written once against `Value` and used directly.

## Source positions

Every token and AST node carries a `SourcePos` (`internal/source`):

```go
type SourcePos struct {
    File   *Source // the file the span belongs to
    Start  int     // byte offset of the first character
    Length int     // length of the span in bytes
}
```

Two positions in the same file can be joined with `a.To(b)`. This is how a node
computes its own extent from its children, and how positions thread through
lowering and the bytecode's position pool so a *runtime* error can still point
back at the exact sub-expression that caused it.

`Log(msg, pos, severity)` is the single diagnostic routine used everywhere. It
recovers the line and column from the byte offset, prints the offending source
line, and underlines the span in colour.
