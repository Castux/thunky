# 7. Type Analysis

Thunky has no types to check. There is one primitive (the number), one
constructor (the tuple), no declarations, and a lambda may accept whatever its
patterns happen to match. But programs are not written that way: every function
in the standard library is built with a shape in mind, and that shape travels
from function to function. `internal/types` recovers it.

The analysis runs on the resolved AST — after [3.Resolver](3.Resolver.md), before
lowering — because that is the last form that still has source positions and
names for everything. It never fails and never stops a program: it is an
inspection mode (`--types`, `--types-all`), not a gate.

## What a type is

A type is a **set of alternatives**, not one constructor. A value in this
language legitimately has several shapes at once: a multi-case lambda accepts
the empty tuple *and* a pair, `if` returns whichever branch ran. So a type node
carries:

| Alternative  | Meaning                                         |
| ------------ | ----------------------------------------------- |
| `num`        | can be a number                                  |
| `tuples[n]`  | can be a tuple of arity `n`, with these fields   |
| `fun`        | can be a function, with this argument and result |
| `top`        | could be anything — the analysis gave up here    |

A node with no alternatives at all is a **variable**: nothing has constrained it
yet. That makes the join total — it never fails, it only widens — which is what
makes the analysis usable on a language where `{ 0 -> 'a', n -> n }` is ordinary
code. Printed, the alternatives are separated by `|`:

```text
maybe.isMaybe : [] | [a] -> Num
```

Nodes are merged by union-find, and **the graph may be cyclic**. That is how a
list is expressed: the argument of `length` is the empty tuple joined with a
pair whose second field is that same node again. No separate recursive-type
machinery exists — the cycle *is* the recursion.

## How a type is written

Types print in the language's own notation, and nothing else:

| Written       | Means                                              |
| ------------- | -------------------------------------------------- |
| `[]`          | the empty tuple, which is also the empty list      |
| `[a, b]`      | a tuple                                            |
| `[a; b]`      | a list of known length — nested pairs ending in `[]` |
| `a -> b`      | a function                                         |
| `a \| b`      | either — the join lattice's whole point            |
| `Num`         | a number                                           |
| `?`           | anything; the analysis gave up here                |

There is deliberately **no notation that asserts a list**. Writing a cycle as
`[a]` claims something stronger than the structure says, and silently collapses
two different types — "terminated by `[]`" and "goes on forever" — into one
text. Cycles are lifted into named equations instead, abstracted over whatever
is not the recursion, and printed once above the report:

```text
-- recursive types
  T1 a : [] | [a, T1 a]        a list
  T2 a : [a, T2 a]             an infinite list, which is NOT the same type
```

so that a signature stays exactly true and still readable:

```text
  map    : (a -> b) -> T1 a -> T1 b
  repeat : a -> T2 a
  cycle  : T1 a -> T2 a
  zip    : T1 a -> T1 b -> T1 [a, b]
  head   : [a, b] -> a
```

`head`'s type is worth a look: it needs only a pair, not a list, and now says
so. The equations are interned by shape, so one `T1` serves every list in a
report however many element types it is used at. A cycle too tangled to
abstract — mutual recursion, mostly — falls back to an inline `mu r1. …`.

Fixed-length lists keep the literal syntax, because that abbreviation is exact
rather than an assumption: `[Num; Num]` and `[Num, [Num, []]]` are the same
type, written the two ways the language writes the value.

## Where the information comes from

Everything concrete enters through the builtins (`builtins.go`): `add` is
`Num -> Num -> Num`, `stdin` is `[Num]`, `string` is `a -> [Num]`, and so on.
Every other type in the library is a consequence of those signatures meeting the
literals and the patterns. A pattern contributes the shape it matches, an
application flows the argument's shape into the parameter, and a multi-case
lambda joins its cases: the domain is the union of the patterns, the codomain
the union of the bodies.

## Generalisation

Bindings are inferred **on demand**, the first time something refers to them, so
definitions are visited in dependency order without anyone sorting them. A
reference that arrives while a binding is still being inferred is a recursive
one and gets the binding's own node, un-copied — that is what ties the knot that
turns `length`'s argument into a list instead of an ever-deeper pile of pairs.

Once a binding is finished it is generalised, and later uses get a copy, which
is what lets `id` be used at one type here and another there. Generalisation is
by **level**: a node created inside the binding is quantified, a node borrowed
from an enclosing scope is not. Unification pushes levels down into the parts of
a type it merges — without that, `fix = f -> let x = f x in x` reports
`(a -> a) -> b` instead of `(a -> a) -> a`, because `x`'s type would be
quantified even though it is tied to `f`'s parameter.

## What it gets right

Most of the standard library, exactly:

```
map         : (a -> b) -> [a] -> [b]
foldr       : (a -> b -> b) -> b -> [a] -> b
T1 a   : [] | [a, T1 a]
T2 a b : [] | [a, b, T2 a b, T2 a b]

mapFilter   : (a -> [] | [b]) -> T1 a -> T1 b
find        : (a -> Num) -> T1 a -> [] | [a]
lookup      : a -> T1 [b, c] -> [] | [c]
compose     : (a -> b) -> (c -> a) -> c -> b
curry       : ([a, b] -> c) -> a -> b -> c
lines       : T1 Num -> T1 (T1 Num)
splitWith   : (a -> Num) -> T1 a -> T1 (T1 a)
heap.merge  : (a -> a -> Num) -> T2 Num a -> T2 Num a -> T2 Num a
```

The heap's node shape — rank, value, left, right, recursively — falls out of the
pattern matches without anything being declared, and `T2` names it: a leaf or a
four-field node with two sub-heaps. Booleans read as `Num`, which is what they
are. `maybe` reads as `[] | [a]`, which is also what it is.

## What it gets wrong, and why

**`core.case`.** The `case … else …` chain is a variadic state machine: it takes
a condition and a value, and then either another pair or nothing, and the
distinction is a *value* (`else` is the number 2), not a shape. The analysis
folds the chain into one recursive function type, `T a : a -> T a -> T a`,
and every value passed to it looks like a mismatch. Conflict reporting therefore
ignores parameters whose type is a function that can reach itself; without that
suppression the corpus produces about 230 warnings, all of them this.

**Tagged unions.** `json` represents a value as `[tag, content]` where the tag
decides what the content is. The analysis is flow-insensitive: it joins every
branch's content into one node, so `quote content` — reached only when the tag
is `"string"` — looks like it is being handed a number. Two of the six warnings
the corpus still produces are this, and they are honest reports of a limitation
rather than bugs.

**Predicates that accept anything.** `list.isList` is inferred as `[a] -> Num`
from its own pattern matches, so `isList 42` — the point of which is to return
0 — is reported as a mismatch.

**Domains are joined, not intersected.** When two different functions reach the
same name, their argument types are joined rather than intersected. This keeps
the result readable and is the right direction for a shape report, but it is an
approximation, not a sound over- or under-estimate.

## Conflicts

Two things get reported (`--types` prints them after the signatures):

- applying something that is definitely not a function;
- passing a value whose alternatives are disjoint from the parameter's — a
  number where a tuple is wanted, say.

Anything unknown on either side is not a conflict: silence is the right answer
when the analysis does not know. Across the whole `examples/` corpus this leaves
six reports, four of them the limitations above and two of them deliberate
(`core_tests` checks that `isList 42` is 0).
