# 7. Type Analysis

Thunky has no types of its own to check. There is one primitive (the number),
one constructor (the tuple), no declarations in the language proper, and a lambda
may accept whatever its patterns happen to match. But programs are not written
that way: every function in the standard library is built with a shape in mind,
and that shape travels from function to function. `internal/types` recovers it —
and, where the author has written the shape down, checks that the program stays
inside it.

Both halves matter, and the second is the reason the first exists. Recovering a
shape gives a report; checking a claim catches the call that will fail. What is
checked is what a `-->` comment declares, so the strength of the analysis over
any one file is a function of how much of it is annotated. The standard library
is annotated in full (394 of 394 signatures), which is why a program that uses it
is checked even when the program itself carries no annotations at all.

The analysis runs on the resolved AST — after [3.Resolver](3.Resolver.md), before
lowering — because that is the last form that still has source positions and
names for everything. It never fails and never stops a program: it is an
inspection mode (`--types`, `--types-all`), not a gate. Nothing below changes
that. A report is the output; a wrong program still compiles and runs.

## What a type is

A type is a **set of alternatives**, not one constructor. A value in this
language legitimately has several shapes at once: a multi-case lambda accepts
the empty tuple *and* a pair, `if` returns whichever branch ran. So a type node
carries:

| Alternative  | Meaning                                         |
| ------------ | ----------------------------------------------- |
| `num`        | can be a number                                  |
| `tuples[n]`  | can be a tuple of arity `n`, with these fields   |
| `fun`        | can be a function, with this argument and result |
| `top`        | could be anything — the analysis gave up here    |

A node with no alternatives at all is a **variable**: nothing has constrained it
yet. That makes the join total — it never fails, it only widens — which is what
makes the analysis usable on a language where `{ 0 -> 'a', n -> n }` is ordinary
code. Printed, the alternatives are separated by `|`:

```text
maybe.isMaybe : [] | [a] -> Num
```

Nodes are merged by union-find, and **the graph may be cyclic**. That is how a
list is expressed: the argument of `length` is the empty tuple joined with a
pair whose second field is that same node again. No separate recursive-type
machinery exists — the cycle *is* the recursion.

## How a type is written

Types print in the language's own notation, and nothing else:

| Written       | Means                                              |
| ------------- | -------------------------------------------------- |
| `[]`          | the empty tuple, which is also the empty list      |
| `[a, b]`      | a tuple                                            |
| `[a; b]`      | a list of known length — nested pairs ending in `[]` |
| `a -> b`      | a function                                         |
| `a \| b`      | either — the join lattice's whole point            |
| `Num`         | a number                                           |
| `?`           | anything; the analysis gave up here                |

There is deliberately **no notation that asserts a list**. Writing a cycle as
`[a]` claims something stronger than the structure says, and silently collapses
two different types — "terminated by `[]`" and "goes on forever" — into one
text. Cycles are lifted into named equations instead, abstracted over whatever
is not the recursion, and printed once above the report:

```text
-- recursive types
  T1 a : [] | [a, T1 a]        a list
  T2 a : [a, T2 a]             an infinite list, which is NOT the same type
```

so that a signature stays exactly true and still readable:

```text
  map    : (a -> b) -> T1 a -> T1 b
  repeat : a -> T2 a
  cycle  : T1 a -> T2 a
  zip    : T1 a -> T1 b -> T1 [a, b]
  head   : [a, b] -> a
```

`head`'s type is worth a look: it needs only a pair, not a list, and now says
so. The equations are interned by shape, so one `T1` serves every list in a
report however many element types it is used at. A cycle too tangled to
abstract — mutual recursion, mostly — falls back to an inline `mu r1. …`.

Fixed-length lists keep the literal syntax, because that abbreviation is exact
rather than an assumption: `[Num; Num]` and `[Num, [Num, []]]` are the same
type, written the two ways the language writes the value.

## Naming shapes: `-->` annotations

A generated `T1` is exact but anonymous. A comment whose first characters are
`-->` gives a shape a name:

```text
--> List a = [] | [a, List a]
--> Maybe a = [] | [a]
--> Stream a = [a, Stream a]
```

and the report uses it wherever that shape occurs:

```text
-- types
  List a   = [] | [a, List a]   (declared)
  Maybe a  = [] | [a]           (declared)
  Stream a = [a, Stream a]      (declared)

  map    : (a -> b) -> List a -> List b
  find   : (a -> Num) -> List a -> Maybe a
  lookup : a -> List [b, c] -> Maybe c
  cycle  : List a -> Stream a
```

**A declaration changes no inference.** It names a shape and decides what that
shape is called when printed; the analysis runs exactly as before. So an
annotation cannot make a working program fail to analyse, and — the thing worth
being explicit about in a dynamically typed language — it cannot narrow what a
function is found to accept. A heterogeneous list keeps its union element type
with `List a` in scope; the element is a union, and unions are first-class in
the notation. `internal/types/annot_test.go` pins that property.

A **signature** is the other kind of annotation and does not work this way: it
participates in the analysis, and is checked. The split is deliberate — naming a
shape is cosmetic and should stay report-wide and harmless, while claiming one
about a binding is a statement that has to earn its keep. See *Checking a claim*
below.

Two conventions stand in for a keyword, both already true of the codebase:

- **A capitalised name is a type.** No value binding in the standard library
  starts with a capital (386 of them, none), and the printer already emits `Num`.
- **`=` means "is defined as"**, exactly as it does for a binding.

So nothing is reserved, and deleting the dashes leaves a line that could become
real syntax later without making a keyword of anything.

### Why the marker is `-->`

It continues `->`, the language's most characteristic symbol; it leaves `:` and
`=` each meaning exactly one thing; and it points forward, which is how a
signature will attach to the binding below it. Every candidate marker was
checked against the corpus first — `-->`, `--!`, `--:` and `----` had zero
existing occurrences, `-- type` had two.

### How the comments are found

The lexer records the span of every comment it skips on the `Source`
(`Source.Comments`). The token stream still carries no comments — they are not
syntax — but the analyser needs to know exactly where they were, and re-scanning
the text would take a `-->` inside a string literal for an annotation. That is a
tested case.

### Two names for one shape

Structural aliasing is not avoidable and the analysis does not pretend
otherwise. `Text = [] | [Num, Text]` and `List a` applied at `Num` are the same
type, so both names fit every string. The report says so rather than choosing in
silence:

```text
alias.th:1:1: List and Text name the same shape; List is used. Structurally
they are one type — if they should differ, one of them needs a tag in the value.
```

which is also the argument against declaring `Text` at all: it would name
`sum : List Num -> Num` as `sum : Text -> Num`. A name that fits a shape fits
every value of that shape, wanted or not. Real distinction needs a tag in the
value — `["point", [x, y]]` — which the language already supports and `json`
already relies on.

The same name declared twice with different bodies is reported too, since one of
the two is not taking effect. Declared identically twice, it is not.

## Checking a claim: signatures

A `-->` comment naming a binding claims a shape for it, and the claim is checked:

```text
module

--> List a = [] | [a, List a]

--> map : (a -> b) -> List a -> List b
map = f -> { ... },
```

This works for any binding, a module's or a `let`'s. Every named value is
reported, and every one of them can be annotated.

A signature attaches to the binding below it — adjacency, the doc-comment
convention, not scope — and must name it, so a signature that has drifted away
from its definition is reported rather than silently checking the wrong thing.

**A signature is authoritative.** Every use of an annotated binding — including a
recursive one — is served a fresh copy of the declared type rather than of
whatever its body inferred to. That is a deliberate reversal of what a *type
declaration* does: `--> List a = …` names a shape and changes no inference
(`annot_test.go:TestDeclDoesNotChangeInference` pins it), while `--> map : …`
participates. Naming is cosmetic; claiming is not.

The reversal is what makes the analysis a check rather than a report, and it
pays for itself three times over.

- **The declared type is exact.** An inferred parameter type is whatever joining
  every call site arrived at, which is both narrower than intended — `isEmpty`
  matches only `[]`, so inference says that *is* its domain — and polluted by
  other callers. Checking an argument against it produces noise; checking against
  the declaration does not. Measured over `examples/`, using inferred domains
  gives 43 reports that are all false; the same check against declared domains
  gives none of them, and removes four reports the older analysis already made
  about `isList`, `isMaybe` and `text.render`, each of which declares `a` and
  means it.
- **It propagates.** `some 5` on its own is a 1-tuple. Through
  `some : a -> Maybe a` it is a `Maybe Num`, so `reverse (some 5)` is caught with
  no annotation anywhere near the call.
- **Recursion needs no knot.** A recursive call is served from the declaration,
  so a definition no longer has to be entered at the right point for its type to
  come out right, and an annotated module could be checked in any order.

What it costs is that a signature can now be wrong in a way that matters, so
there are two checks keeping one honest, and they pull in opposite directions
because subtyping does:

| Direction | What is checked | Where |
| --------- | ---------------- | ----- |
| covariant (results) | what the body produces is something the signature allows | `checkGiven`, `check.go` |
| contravariant (domains) | what the signature promises to accept, the patterns match | `checkExhaustive`, `exhaust.go` |

These are two halves of one relation — `inferred <: declared` — and neither means
much alone. Call sites are checked against the declaration, so a declaration
wider than the code behind it is a lie every caller inherits; that is what
exhaustiveness rules out. A declaration narrower than the code is caught on the
way out:

```text
core/list.þ:150:1: map : (a -> b) -> List a -> Num does not hold —
the result: the empty tuple or a pair is not admitted
(inferred (a -> b) -> List a -> List b)
```

Two things still claim nothing, and so never contradict: a type **variable**, and
`?`, which is rejected outright in a signature since it would always check out
and hide the mistake it was meant to catch.

### Containment, and why it has variance

The relation underneath all of this (`domain.go`) is: does `got` admit any shape
`want` does not? It replaced an older test for *disjointness* — do these two have
no shape in common? — which is the right question for a report that only wants to
name outright contradictions and the wrong one for a check. Two cases say why.

```text
reverse (some 5)          -- Maybe and List overlap, on []
length [[1, 2], [3, 4]]   -- a 2-tuple of pairs overlaps a list, at the top
```

Neither is disjoint from what the callee takes, and both fail at run time; the
second with `no pattern matched value 4`, two levels down, where a number stands
where the tail of a list has to be. Containment differs in two ways that are not
optional.

**It is recursive by necessity.** The second example is wrong only at depth. The
descent stops on *knownness*, not depth: a variable or `?` on either side ends
it, because nothing there is claiming anything that could be violated. Both
graphs may be cyclic — a list *is* a cycle — so the walk is coinductive, assuming
a pair holds while it checks it.

**It has variance.** `got <: want` for a function means the supplied function
must accept at least what the declaration promises to hand it, so the argument
position recurses with the two sides swapped:

```text
useOnList : (List Num -> Num) -> Num

{ [] -> 0, [h, t] -> 1, n -> 0 }   accepts more than required — fine
n -> add n 1                       accepts less
  the argument: the empty tuple or a pair is not admitted
```

Disjointness is symmetric and could ignore this. Containment cannot, and getting
it wrong would reject correct higher-order code, which in `list` is most of it.

### Carried, consumed, concrete

A signature's variable becomes one node across the whole type, which is what
carries `Num` from the argument of `reverse : List a -> List a` to its result.
Two arguments meeting at that node are *joined*, not required to agree — and
whether that is right depends on what the callee does with the variable. There
are three strengths of position, and getting them mixed up is what a first
attempt gets wrong in both directions.

| Position | Held to | Because |
| -------- | ------- | ------- |
| declared concrete — `List a`, `Num`, `[a, b]` | containment, at every depth | the author wrote it and nothing else writes to it |
| a **consumed** variable — `a` in `map` | disjointness | concrete only because an earlier argument made it so |
| a **carried** variable — `a` in `if` | nothing | the callee never looks at it |

A variable is **carried** when the callee only moves it: `if : Num -> a -> a -> a`
takes `a` from whichever branch comes first and hands it straight back, so
`if c (some x) none` is ordinary code whose result is the union. Requiring the
second branch to match the first would make that an error.

A variable is **consumed** when the callee hands it to the caller's *own*
callback before returning. `map : (a -> b) -> List a -> List b` puts the elements
of the caller's list into the caller's function, so

```text
map (n -> add n 1) [[1; 2]; [3; 4]]
  passed [[Num; Num]; [Num; Num]] to map, which takes List Num
  — field 1 of the pair: a pair is not admitted
```

is a real clash and is reported. The two are told apart by **polarity**
(`consumedVars`): a variable is consumed when it occurs positively somewhere
other than the result spine — positive meaning the callee produces a value there,
off the spine meaning it does so before returning. `a` in `if` occurs positively
only as the result; `a` in `map` occurs positively as the callback's domain,
which is inside an argument.

A consumed variable is checked, but only for **disjointness**, because its value
is still assembled by joining and is never complete while the arguments are being
read one at a time. Two things depend on that being the weaker test:

```text
partition = foldr (x -> [ts, fs] -> [[x, ts], fs]) [[], []]
```

`foldr`'s `b` is consumed by the step function *and produced by it*, so by the
time the seed `[[], []]` is checked, `b` already carries the step's result — a
pair of cons cells, never `[]`. The seed is not contained in that, and it is not
wrong either: `b` is the union of both. And a callback that matches a narrower
shape than the element type admits — `map ([a; b; c; d; e] -> …) rows`, five
sites in `zebra-puzzle` alone — is how the library is written, not a mistake.
Disjointness passes both and still catches a number meeting a list.

Both marks live on the node (`Type.fromVar`, `Type.weak`) and are deliberately
*not* unioned by `join`: they record what a signature wrote, and a value that has
passed through a polymorphic position has not thereby become unknown.

### Checking a call

An argument is checked against the parameter it fills when the callee is
**trusted** — a builtin, or a binding with a signature — because only then is the
parameter type the author's and freshly instantiated for this call. Everything
else is held to disjointness, as before.

```text
test.th:7:8: passed Maybe Num to reverse, which takes List a
test.th:2:31: passed [[Num, Num], [Num, Num]] to length, which takes List a
  — field 2 of the pair of field 2 of the pair: a number is not admitted
```

A partial application stays trusted, since it is the same instantiated signature
one argument further along. Checking happens *before* the argument is joined into
the parameter — the join is what instantiates the signature's variables, and by
the time it has run the two nodes are one and there is nothing left to compare.

The same walk that checks the call also carries the element type out through the
result, which is the half of a call that is not a check at all: `reverse [1; 2; 3]`
is `List Num` because both `a`s in the signature are one node.

### Checking a body

A body is inferred *against* its signature, not merely compared with it
afterwards. The declared argument type is pushed into the patterns before their
binders are read, so

```text
--> last : List a! -> a
last = { [x, []] -> x, [h, t] -> last t }
```

gives `h : a` and `t : List a` rather than two fresh variables. This is
refinement by the shape of a pattern: it needs no flow analysis, no knowledge of
what the other cases matched, and no case ordering. The codomain is deliberately
*not* seeded — joining it with the declared result would merge the claim into the
finding and leave nothing to check.

Refinement by *residual* — knowing that `l` is non-empty in
`{ [] -> …, l -> f l }` because the earlier case consumed `[]` — is not done, and
is not planned. The standard library is written to match the cell it needs
instead, which is shorter, states the fact where a reader sees it, and is the
same discipline that discharges a `!` at a call site.

### A given signature is what gets displayed

An annotated binding is reported as *its signature*, not as the inferred shape.
That is what makes annotating a library worth the effort: the report becomes the
documented interface, verified, rather than a restatement of whatever inference
happened to find.

It also matters because inference is often *broader* than intent. `count`'s
argument infers as `List [Num, a]` when a pair's second field goes unused; the
signature `List [Num, Num] -> Num` is narrower, true, and what a reader wants.

A contradicted signature is still shown as written — it is what the author claims
— with the finding underneath:

```text
  map         : (a -> b) -> Num -> List b
                ^ does not hold; inferred (a -> b) -> List a -> List b
```

Hiding the claim would make the report disagree with the source; hiding the
finding would make the disagreement invisible. The warning section carries the
detail and the position.

Provenance is summarised once rather than marked per line, because after a
library is annotated most types are the author's:

```text
-- 5 of 306 module types are given signatures; 301 inferred
```

One consequence worth naming: displaying a signature means nothing ever
*renders* the shapes it mentions, so the declared types it names have to be
pulled into the preamble deliberately. Otherwise a report would print
`List Num -> List Num` with no equation saying what `List` is.

### Exhaustiveness, and the `!` mark

A signature is a claim about the domain, so it is also the specification the
patterns have to cover:

```text
--> last : List a -> a
last = { [x, []] -> x, [h, t] -> last t }
```

```text
core/list.þ:52:1: last : List a -> a — argument 1 does not cover the empty
tuple of what it claims; handle it, or write `!` after that type to assert it
anyway
```

**This is the part comparing types cannot do.** It is the contravariant half of
`inferred <: declared`, and it has to be done against the patterns rather than
against a node, because pushing the declared domain into the patterns (which is
what makes a binder see the right type) also widens the inferred domain to match
it. The claim and the finding then agree by construction, and only the patterns
still know what was really matched. `head`, `init`, `last`, `maximum`, `minimum`
and `maybe.value` are all found this way.

A `!` suffix says the author asserts that position anyway:

```text
--> head : List a! -> a
--> headSafe : List a -> Maybe a
```

which is the trade the language lives on: `head` over a list is more useful than
`headSafe` alone, and the mark says out loud that the caller carries the
assumption. The pair now reads as two different promises rather than two similar
types.

**Precedence.** `!` binds to the whole type at its position, so `List a!` means
`(List a)!` — an assertion about the argument, not about its element. Both
spellings are accepted; `List (a!)` is how you would mark the element instead.
A `!` on a bare type variable is an error, since a variable claims nothing and so
cannot over-claim.

**On a result**, the mark means the other thing the analysis cannot confirm: a
claim *narrower* than what joining could ever show.

```text
--> cycle : List a -> Stream a!      Stream a = [a, Stream a]
```

`cycle` really does return an endless list, never `[]`, and nothing in a lattice
that only widens will demonstrate it. Without the mark the covariant check
reports the signature; with it, the claim is the author's. It is the same
sentence in both positions — *checked by the author, not by me* — and the only
difference is who inherits it: an argument's mark propagates to callers
(next section), a result's stops here.

The marks are totalled, so the assumptions a project rests on stay countable
rather than accumulating unnoticed:

```text
-- 394 of 394 module types are given signatures; 0 inferred
-- 12 position(s) in 12 signature(s) asserted with `!`
```

Exhaustiveness is skipped when the claim is *contradicted* on the way out: the
patterns cannot cover a domain the code does not accept, and offering `!` as the
remedy for a plainly wrong type is how the mark would become a rubber stamp.

### Propagating a mark to the caller

Exhaustiveness sees only a binding's own patterns, so it has nothing to say about
a function that is partial *by delegation*: `nth = n -> drop n *> head` never
matches on the list, it calls `head`. A second pass (`assert.go`) covers that
case. It walks every call site, and when the callee asserts the position an
argument fills, the caller inherits the assumption and its signature has to say
so:

```text
core/list.þ:501:20: argument 1 of head is asserted with `!`, and nothing here
rules the assumption out, so nth inherits it; mark nth with `!` too, or call
something total
```

Without this a library could launder every assumption by wrapping it in one more
function, and marks would only ever appear on the handful of definitions that
pattern match incompletely.

**Discharging** is what keeps the mark meaningful. A call is safe when the
argument is *built right there* in a shape the callee matches:

```text
lastSafe = {
    [] -> maybe.none,
    [h, t] -> maybe.some (last [h, t])
}
```

`last` matches a pair and nothing else; `[h, t]` is written as a pair; so nothing
is being assumed, and the reason the reader believes the call is safe is the
reason the analysis accepts it. The same rule covers `char '0'`, since a non-empty
string literal is a list cell and never `[]`. This is why the safe wrappers in
`list` rebuild the cell they just matched rather than passing the argument along:
the reconstruction is what carries the evidence.

The shape is read off the **source**, not off the argument's inferred type,
because by the end of the walk that type says nothing useful. Passing
`[h, t]` to `last` joins the two nodes, so the argument ends up carrying `last`'s
`List a` — empty case and all. The narrower fact exists only at the syntax.

An **alias** inherits its target's patterns, so `char = head` discharges exactly
as `head` does; and an alias with no call site at all is checked directly, since
otherwise every caller would see `char`'s signature and none would see `head`'s.

**What cannot be discharged is left undischarged.** `nth`'s assumption is a
relation between the index and the length, not a claim about shape: `nth 5
[1; 2; 3]` fails with a perfectly good non-empty argument, so a shape rule would
wrongly call that call site safe. Nothing discharges it, every caller inherits
it, and that is the honest answer rather than a gap to close. It is also why the
library grew `nthSafe` and `nthOr`.

Composition (`*>`) is treated the same way: there is no expression for the
argument at all, so nothing can be known about it and the assumption stands.

### The limit that remains

**Exhaustiveness is relative to the declared domain.** Silence means "the
patterns cover what you claimed", not "this function is total". Those coincide
only when the claim is honest — which is exactly why the covariant half of the
check exists, and why the two are described together above.

Refinement by residual is still absent: in `{ [] -> …, l -> f l }` the analysis
does not know that `l` is non-empty on the second branch. Refinement by *shape*
is done (see *Checking a body*), which covers the case the library actually
writes; the residual case is left to the same rewriting discipline that
discharges a `!`.

### Scope

Type names in a signature resolve exactly as value names do: the unit's own
declarations, then those of the modules it imports (a later import shadowing an
earlier one), plus qualified `module.Name` for anything in the import clause.
Nothing new to learn, and nothing new to implement conceptually.

Declarations are still gathered report-wide for *display* — a name is not a
semantics, and sharing them keeps one name for one shape across a report — while
*resolution* is per unit. That split is deliberate: cosmetic naming is global,
checking is scoped.

### A declaration may name another

A body may name any type in scope, so the library's types are written the way you
would describe them:

```text
--> BigInt = [Num, List Num]
--> BigFloat = [BigInt, Num, Num]
--> Table k v = List [k, v]
```

Collection is therefore two passes: heads first, so arities are known, then
bodies in dependency order. A reference is resolved in the declaring unit's own
scope, the same rule as a signature. Mutual recursion between *distinct*
declarations cannot be expanded by substitution and is reported; a declaration
naming itself is the ordinary recursive case and becomes a cycle in the pattern.

Two consequences fall out of this, and both needed handling:

- **A module's own name wins.** `Table k v` *is* a list of pairs, so without a
  preference every list of pairs in the library reads as `Table` — `list.zip` and
  `list.lookup` included. A binding is printed with its own module's
  declarations preferred, which is why `table.get : a -> Table b c -> Maybe c`
  and `list.zip : List a -> List b -> List [a, b]` both read correctly.
- **An alias by construction is not reported.** `Table` and `List` agreeing on a
  shape is the *point* of writing `Table k v = List [k, v]`, so the
  same-shape note is suppressed when one declaration names the other. It still
  fires for a coincidence, which is the case worth knowing about.

### What is not here yet

A signature cannot be attached to anything but a binding. Two positions written
with the same variable *are* now one node, which is what carries an element type
through a call — but see *What it gets wrong* for the sense in which that node is
still a join variable rather than a unification variable.

## Local bindings

A module's public bindings are its interface. Everything else a program names
lives in a `let`, and that is where most of the code is: a module binding is
often one line delegating to a handful of locals, and a program is usually a
single `let` with the whole program inside it.

They are reported under the module they are written in, after its interface, and
named by the path that reaches them:

```text
-- big
  magAdd : List Num -> List Num -> List Num
  ...

  -- let bindings
  magAdd.go            : Num -> List Num -> List Num -> List Num
  floatSqrt.go.next    : BigFloat
```

The path is what makes the list readable — `go`, `step` and `loop` recur many
times over in a library, and a bare name would not say which one is meant.

Nothing extra is inferred for them. The walk forces every binding of every `let`
it enters, so a local has a type whether or not anything refers to it; reporting
is all that is added.

## Where the information comes from

Two sources, and they are checked against each other.

**The builtins** (`builtins.go`) are the ground truth: `add` is
`Num -> Num -> Num`, `stdin` is `[Num]`, `string` is `a -> [Num]`. They are
freshly built at every use, so a builtin is trusted for the same reason a
signature is.

**Signatures** are the author's, and are what most of a report now rests on. A
binding without one is still inferred exactly as before: a pattern contributes
the shape it matches, an application flows the argument's shape into the
parameter, and a multi-case lambda joins its cases — the domain is the union of
the patterns, the codomain the union of the bodies.

The difference is where the two meet. An unannotated binding's type is a
consequence of the builtins meeting the literals and the patterns; an annotated
one's is what it says it is, with those consequences used to check it.

## Generalisation

Bindings are inferred **on demand**, the first time something refers to them, so
definitions are visited in dependency order without anyone sorting them. A
reference to an *unannotated* binding that arrives while it is still being
inferred is a recursive one and gets the binding's own node, un-copied — that is
what ties the knot that turns `length`'s argument into a list instead of an
ever-deeper pile of pairs. An annotated binding needs none of this: the recursive
reference is served a copy of the signature, so the knot is never tied.

Every node a signature builds is generic, so each use gets its own copy and one
signature serves `map` at two element types in the same expression.

Once a binding is finished it is generalised, and later uses get a copy, which
is what lets `id` be used at one type here and another there. Generalisation is
by **level**: a node created inside the binding is quantified, a node borrowed
from an enclosing scope is not. Unification pushes levels down into the parts of
a type it merges — without that, `fix = f -> let x = f x in x` reports
`(a -> a) -> b` instead of `(a -> a) -> a`, because `x`'s type would be
quantified even though it is tied to `f`'s parameter.

## What it gets right

What follows is what *inference alone* finds, with no signature in sight — the
floor the checking rests on, and what an unannotated program still gets:

```
map         : (a -> b) -> [a] -> [b]
foldr       : (a -> b -> b) -> b -> [a] -> b
T1 a   : [] | [a, T1 a]
T2 a b : [] | [a, b, T2 a b, T2 a b]

mapFilter   : (a -> [] | [b]) -> T1 a -> T1 b
find        : (a -> Num) -> T1 a -> [] | [a]
lookup      : a -> T1 [b, c] -> [] | [c]
compose     : (a -> b) -> (c -> a) -> c -> b
curry       : ([a, b] -> c) -> a -> b -> c
lines       : T1 Num -> T1 (T1 Num)
splitWith   : (a -> Num) -> T1 a -> T1 (T1 a)
heap.merge  : (a -> a -> Num) -> T2 Num a -> T2 Num a -> T2 Num a
```

The heap's node shape — rank, value, left, right, recursively — falls out of the
pattern matches without anything being declared, and `T2` names it: a leaf or a
four-field node with two sub-heaps. Booleans read as `Num`, which is what they
are. `maybe` reads as `[] | [a]`, which is also what it is.

## Why the multiway conditional is functions

A chain of conditions is written with `maybe.when` / `elseWhen` / `default`:

```text
when     (magIsZero b) [[], []]
> elseWhen (lt a b)      [[], a]
> default  (divide a b)
```

Each of the three is an ordinary function, so every part of the chain has a type
and the result is whatever the branches are. The alternative — a variadic form
where one writes condition and value pairs until a sentinel — cannot be typed
here, because the *shape* of the next argument would depend on the *value* of the
last one: the analysis can only fold such a chain into a recursive function type,
which then appears in the inferred result of everything that uses it. A `Maybe`
returned through one reads as `[] | [a] | b -> … -> …`, which is not
recognisable as a `Maybe`, and conflict reporting would have to stay silent about
every value passed to a parameter of that shape — silencing genuine errors along
with the noise.

Laziness is not a cost of the choice: `orElse` matches on its second argument and
never touches the first when that is `some`, so nothing after the first true
condition is evaluated.

## What it gets wrong, and why

**Tagged unions.** `json` represents a value as `[tag, content]` where the tag
decides what the content is. The analysis is flow-insensitive: it joins every
branch's content into one node, so `quote content` — reached only when the tag
is `"string"` — looks like it is being handed a number. Three of the nine
warnings the corpus still produces are this. Checking deeper made it worse, which
is the honest trade: every level of descent is another chance to meet a field
that was joined across branches.

Rewriting does not help here, which is worth saying because it does help almost
everywhere else. Matching `["string", content] -> quote content` instead of
testing the tag changes nothing: every case matches a 2-tuple, so field 2 of the
argument is a single node and each case's binder points at it. There is no
per-branch refinement to exploit. This one needs flow sensitivity or an API that
does not mix tags.

**A consumed variable is only checked for disjointness.** `map (n -> add n 1) xs`
is caught when `xs` holds lists, because a number and a tuple share nothing; it
is not caught when the callback matches a 3-tuple and `xs` holds pairs, because
both are tuples and the coarse test cannot tell them apart. Making it finer needs
the two occurrences of `a` — the one the caller fills and the one the callback
consumes — to be separate nodes with a one-way constraint between them, rather
than one node that both write to. That is a constraint solver, not union-find,
and it is the largest remaining gap.

**A homogeneous list type merges what it is given.** `List a` has one element
node, so passing a heterogeneous list unifies its elements with each other.
`format "..." [n; from; to]` in `towers-of-hanoi` makes `n`, `from` and `to` one
type; `n` is a number by then, and the strings are reported at the call site. The
declaration is not wrong — a union is a fine `a` — but destructive unification
reaches the binders before the union is complete. Not merging would cost more
than it saves: it is what makes `f = x -> id x` come out as `a -> a`.

**Predicates that accept anything** used to be reported and no longer are, since
`isList : a -> Num` is now taken at its word. Left here because the reverse
mistake is now possible: a signature that declares more than the code handles is
caught only by exhaustiveness, and only where there are patterns to look at.

**Domains are joined, not intersected.** When two different functions reach the
same *unannotated* name, their argument types are joined rather than intersected.
This keeps the result readable, but it is an approximation, not a sound over- or
under-estimate — and it is exactly why an unannotated callee is held to
disjointness rather than containment.

## Conflicts

Three things get reported (`--types` prints them after the signatures):

- applying something that is definitely not a function;
- passing an argument not **contained** in a trusted parameter — a signature's,
  or a builtin's;
- passing an argument whose alternatives are **disjoint** from an untrusted
  parameter's — a number where a tuple is wanted, say.

Anything unknown on either side is silence, at every depth. The two strengths are
the whole of the design decision: a declared parameter is exact and can be held
to containment, an inferred one is an artefact of joining and can only be held to
the coarse test.

Across `examples/` this leaves nine sites. Three are the flow-insensitive tagged
union in `json` — `stringify` joins every branch's content into one node, so
`quote content` looks like it is handed a number — and one is `json.path`, which
walks with `get` and `at` and says so in a comment. Of the rest:

- `core_tests` calls `maybe.andThen (add 1)`, deliberately, to check that a
  non-`Maybe` result falls through. The test is named `andThen-extract`; the
  report is correct and the code is knowingly outside its signature.
- `aoc06` uses `text.splitWith` on a list of rows. Its signature says
  `(Num -> Num) -> List Num -> List (List Num)` — a string function — while the
  body is generic, so either the signature or the call is wrong. This is the
  class of mistake the check exists for, and the resolution is an API decision
  rather than a fix here.
- `towers-of-hanoi` passes `[n; from; to]` to `format`, whose second parameter is
  `List a`. A list type has one element node, so unifying it makes `n`, `from`
  and `to` one type; `n` is a number, and the strings then do not fit. See *What
  it gets wrong*.
- `sokoban` dispatches on a value.

For comparison, the older disjointness-only check reported seven sites, four of
which were noise: `isList`, `isMaybe` and two `text.render` calls, each declaring
`a` and being exercised exactly as declared. Checking against the declaration
removed all four.

Assertion warnings are counted separately; see the propagation section above.
